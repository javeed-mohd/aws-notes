Important:
=========

Folders are named 00, 10, 20, 30… to control the execution order when running scripts or loops.

==> The command ls lists folders alphabetically, not logically.

==> Ensures Correct Infrastructure Order

Infrastructure components depend on each other.

Example:

Folder      What it creates     Dependency
=====       ===============     ==========
00-vpc      Network (VPC)		    First
10-sg		    Security Groups		  Needs VPC
20-sg-rules	SG Rules		        Needs SG
30-bastion	Bastion server		  Needs VPC + SG
.
.
.
.

==> So developers use numbers at the beginning of folder names to force the correct order.
==> If order is wrong, Terraform may fail because required resources don’t exist yet.

For deletion we use:
==> ls -rd *

So infrastructure is destroyed from top dependency to base dependency, preventing errors.

Numbering folders like 00, 10, 20, 30 helps to:

--> Control execution order
--> Avoid dependency errors
--> Automate scripts easily
--> Destroy resources safely in reverse order...


1. S3 access, state file retrieval, creation, update
2. EC2 creation access(iam role policy attachment)
3. R53 entries creation, deletion, update

Here, (ls -dr *) Lists all folders in the current directory.


To list all in roboshop-infra-dev:
====> ls -dr *  --> Lists all directories in the current project

To delete all then:
====> for i in $(ls -rd *); do cd $i; terraform destroy -auto-approve; cd ..;done

====> for i in $(ls -rd *); do 
cd $i
terraform destroy -auto-approve
cd ..
done

Here, ls -rd * → Lists folders in the reverse order.

Why reverse order?
-> Infrastructure has dependencies.

Example:
-> Bastion depends on Security Group
-> Security Group depends on VPC

So destroy order should be:
-> 30-bastion
-> 20-sg-rules
-> 10-sg
-> 00-vpc

That’s why reverse order (-rd) is used.

Provisioners:
=============

1. LOCAL EXECUTION  ==> local-exec -> Where terraform executes
2. REMOTE EXECUTION ==> remote-exec -> Executes inside the resources created by terraform

Self is the special variable, self refers to the current resource.

Connection block is mandatory to have the ssh protocol access to connect in remote exec.

In Terraform, a connection block is used to define how Terraform connects to a remote resource (usually a VM) to run provisioners like remote-exec or file.

It tells Terraform:
-> Which user to log in as
-> How to authenticate (SSH key / password)
-> Host IP or DNS
-> Connection type (SSH)

Syntax:
~~~~~~~
connection {
  type        = "ssh"
  host        = self.public_ip
  user        = "ec2-user"
  password    = "123456"
}

SSH Connection:
~~~~~~~~~~~~~~~~

resource "aws_instance" "example" {
  ami           = "ami-12345678"
  instance_type = "t2.micro"
  vpc_security_group_ids = [aws_security_group.allow_tls.id]

  provisioner "remote-exec" {
    inline = [
      "sudo dnf install nginx -y",
      "sudo systemctl restart nginx"
    ]
  }

  connection {
    type        = "ssh"
    user        = "ec2-user"
    password = "2131456"
    host        = self.public_ip
  }
}

user-data:
==========

1. Once the system is provisioned, AWS executes the commands inside user_data script.
2. If user_data script is failed, terraform is not aware. terraform is still success.
3. Since AWS runs user_data(aws_instance), we can't get immediate log.
4. Useful for simple installations.


provisioner:
============

1. It is terraform resource.
2. If remote-exec is failed, terraform is also failed.
3. We can get immediate log on the console about what is going on.

TELNET
======
Telnet is a network protocol and command-line tool used to connect to a remote server. It is a TCP-based protocol and tool used to test remote server connectivity and port availability.
