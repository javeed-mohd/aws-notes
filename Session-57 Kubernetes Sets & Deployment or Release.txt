Resources:
==========

Namespace 	--> Isolated project space where we create our project resources.
Pod 		--> Smallest deployable unit in Kubernetes, pod contains multiple containers. Every container share same network and storage.
Labels 		--> Adds metadata to the pods, labels are selectors. We can attach labels to any resource in k8s.
env 		--> We can pass env variables to the containers.
resources 	--> We need to restrict pod resources. Request and limits are soft limit and hard limit.
annotations --> Again adds metadata, but used to select external resources like load balancers, IAM roles, etc.,
config map 	--> Configuration resource, We can attach config map to the pod.
secrets 	--> Confidential information, we can attach to pod environment, but only encoded information not encrypted.


In Kubernetes, a Service is an abstraction that defines a logical set of Pods and a policy to access them (like ClusterIP, NodePort, or LoadBalancer).

A LoadBalancer Service:

==> Exposes your application externally to the internet (or external network).
==> Automatically provisions an external load balancer from the cloud provider (if supported).
==> Routes traffic to the backend Pods.


Services:
=========

1. pod to pod communication since pod ip is ephemeral. We can communicate with service name which acts as DNS.
2. load balancing between pods
3. service select pods based on labels as selectors

1. Cluster IP -> Internally exposing pod with in the cluster. [By default, it acts as cluster ip if nothing specified]
2. Node port -> Cluster IP is subset of nodeport. Every node inside eks cluster open the nodeport. eks node port range ephemereal [30000–32767]. To access an application which is running in kubernetes through browser when a user wants to access it, then user can use nodeport. [Kubernetes service nodeport]
3. Load balancer -> Node port is subset of load balancer. It will create a classic load balancer. It will work only in cloud environment, we need extra configurations to setup in on-premise.


==> ClusterIP: Default, internal access only.
==> NodePort: Exposes service on a port on all nodes (can be combined with external LB manually).

Sets
=====

1. ReplicaSet -> Create multiple replicas of your pod. Always runs desired number of pods. (k8 replicaset)
2. Deployment -> Deployment is the most commonly used controller to manage stateless applications. It provides a higher-level abstraction over ReplicaSets and handles updates, scaling, and rollbacks automatically.
3. DaemonSet  -> A DaemonSet ensures that one pod runs on every node (or selected nodes). (Monitoring, logging events, node-level services)
4. StatefulSet -> A StatefulSet manages stateful applications with stable identity. (Db)

==> We can give labels to any resources in Kubernetes.


1. ReplicaSet: (k8 replicaset) ==> A ReplicaSet ensures a specified number of identical pods are always running.
===============

A ReplicaSet is a concept for ensuring high availability and scaling of your application Pods.

--> Ensures that a specified number of pod replicas are running at any given time.
--> Automatically replaces pods that fail or are deleted.
--> Provides declarative scaling


replicas: 3 → Kubernetes ensures 3 pods are always running.

--> You create a ReplicaSet.
--> Kubernetes checks how many Pods already exist matching the selector.
--> If less than replicas, it creates new Pods.
--> If more than replicas, it terminates extra Pods.
-->If a Pod crashes, Kubernetes automatically replaces it.


ReplicaSets are usually managed by Deployments. You rarely create them directly.

Deployment → manages ReplicaSets → manages Pods.
This allows rolling updates, rollbacks, and declarative version control.

For manual: kubectl scale replicaset my-app-rs --replicas=5

Deployment/Release: (k8 deployment)
===================

You have v1 running, v2 is ready

1. Stop the application server or component. systemctl stop catalogue
2. Remove the v1 code
3. Download v2 code
4. Restart catalogue. systemctl restart catalogue

Since pods are immutable, we can create another set of v2 pods, then delete v1 pods.

Features:
~~~~~~~~~

1. Rolling Updates
Updates pods gradually (no downtime if configured well)
Old version is replaced step by step

2. Rollback
Easily revert to a previous version
kubectl rollout undo deployment <name>

3. Scaling
Increase/decrease pod count easily
kubectl scale deployment my-app --replicas=5

4. Self-healing
Replaces failed pods automatically
