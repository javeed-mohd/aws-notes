Best practices:
===============

Including resources, probes (Health checks) are also best practices.

Liveness, Readiness and Startup probe (liveness and readiness probes)

==> liveness probe 	--> Every 5 sec, check the server is running or not -> Health check

==> readiness probe	--> Is your app ready to handle traffic? Usually app takes some time to start/get ready.

==> startup probe	--> Usually java apps or high memory apps take some more time to start ==> For running the image, it takes some time to start for that we use startup probe.

Flow: startup -> readiness -> liveness
~~~~~

1. if 8080 is opened then app is running (port opened or not)
2. /health is giving response then app is running --> preferable (http url)


How They Work Together:
=======================

Phase               Probe Used          Behavior
======              ===========         ========
App starting        Startup Probe       Waits until app is up
Running             Liveness Probe      Restarts if broken
Serving traffic     Readiness Probe     Controls traffic flow


==> Liveness Probe: A liveness probe checks whether a container is still running properly. If it fails, Kubernetes restarts the container.

==> Readiness Probe: A readiness probe checks whether a container is ready to accept traffic. If it fails, Kubernetes stops sending requests to that container.

==> Startup Probe: A startup probe checks whether a container has successfully started. It is used for slow-starting applications and prevents premature restarts during initialization.


==> Startup ensures the app starts correctly, readiness ensures it serves traffic safely, and liveness ensures it stays healthy.

==> For a slow-starting application, I would use a startup probe to allow initialization, a readiness probe to delay traffic until dependencies are ready, and a liveness probe to restart the container if it becomes unresponsive later.


When Would You Use All Three?

==> When the application has a slow startup time and needs proper health monitoring to avoid downtime and unnecessary restarts.


What is a Liveness Probe?
==> A liveness probe checks whether the container is still running correctly, and if it fails, Kubernetes automatically restarts the container to recover from failures like deadlocks.

What is a Readiness Probe?
==> A readiness probe determines if a container is ready to serve traffic, and if it fails, Kubernetes removes the pod from the service so it doesn’t receive requests.

What is a Startup Probe?
==> A startup probe verifies whether the application has started successfully, preventing the liveness probe from restarting slow-starting containers too early.

Difference Between All Three
==> Startup probe handles initialization, readiness probe controls traffic, and liveness probe ensures the application stays healthy by restarting it if needed.

ImagePullPolicy:
================

==> In Kubernetes, the imagePullPolicy for a container determines when the kubelet attempts to pull (download) the specified image from a registry. 

Supported Policies
~~~~~~~~~~~~~~~~~~~
There are three possible values for this setting:

Always: Every time the container starts, the kubelet queries the registry to check the image's digest. If the local image matches the registry, it uses the cache; otherwise, it pulls the new image. 

IfNotPresent: The image is pulled only if it does not already exist on the node. This is common for production to save bandwidth and speed up startup. 

Never: The kubelet does not attempt to pull the image. It assumes the image is already pre-loaded on the node; if it isn't, the Pod fails with an ErrImageNeverPull error.

==> Without configmap file (nginx.conf) in frontend/manifest.yaml, we should run and check. We will get the response as loadbalancer url to check the roboshop application on the browser...

But, if we make any configuration changes in nginx.conf file of frontend in docker image, then we have to rebuild the image, push the image to hub and then pull the image by running manifest.yaml file of frontend (restart the Pod).

==> To use in configmap, we cannot keep files in configmap same as key-value pairs. If we want to keep files then we have to add as volume nginx.conf (volume=data=disk), then we tell nginx container to mount nginx.conf file (we will keep it as volume which in turn has data in it). Container to volume mount and get the data from it...

==> Advantage by using this is that we need not rebuild the image from docker... We can directly make changes in configmap and push the changes...

In configMap, we have add volumes in specifications in container level with a proper name and we have to mount it to the container we want by providing volumeMounts and give it a name, mountPath and readOnly as true...

==> By doing this, in future if any configuration changed, we need not rebuild the image in docker rather than doing that we will edit the changes in configMap and restart the container.


It should be pod-level in specifications:

volumes:
- name: nginx-config
  configMap
    name: frontend


This should be in containers which will help volumes to mount.
volumeMounts:
- name: nginx-config
  # By default it mounts and thinks as directory
  mountPath: "/etc/nginx/nginx.conf"
  subPath: nginx.conf
  readOnly: true


**** First, we have to run the manifest.yaml file of frontend without configMap, volumeMounts and volumes and further you can use it after running from next time when we make any changes in configuration, we can directly edit in the configMap itself and restart the container rather than rebuild the image in docker...

==> Then we have to apply frontend/manifest.yaml file after making any configuration changes...

Edit in nginx.conf -> Apply -> Restart the container

==> nginx.conf (key) -> value is the nginx.conf file
