RBAC:
=====

Role -> Authorisation service in k8s which can control permissions. which api group, which resource inside api group, what actions user can perform on resources
Role Binding -> Map user to role
aws auth -> Map IAM users to K8 users
Cluster Role -> Cluster level resources permissions control
Cluster Role Binding -> Map user to cluster role
Service Account -> An identity to pod, pod can have service account that maps with IAM role

hostpath based routing:
=======================

amazon.joindevops.com -> amazon

ALB -> Listener -> evaluate rule -> target group -> VM - Instances
ALB -> Listener -> evaluate rule -> target group -> Pod - IP

Instance mode:
ALB talks to machines, machines route to containers.
IP mode:
ALB talks directly to containers (pods).

3. Create service account:
---------------------------

eksctl create iamserviceaccount \
--cluster=roboshop \
--namespace=kube-system \
--name=aws-load-balancer-controller \
--attach-policy-arn=arn:aws:iam::<AWS_ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy \
--override-existing-serviceaccounts \
--region us-east-1 \
--approve

<AWS_ACCOUNT_ID> -- 996669628469 --> replace with your AWS ID

If we want application running inside k8 to be exposed to internet, we need ingress resource that can route http/https requests to pods. Actually through annotations, we can select external resources like Application Load Balancer (alb), listener, target group, certificate arn, etc.

--> Ingress talks to ingress controller drivers, that will have service account mapped to IAM role and permission to create the resources like reading secret values.

Service account is Pod identity, instead of configuring human credentials we can attach service account to the pod that can access external resources like reading secret values -> It is non human role.

Terraform-AWS-EKS:
==================

Replacing the entire VM's used in roboshop-infra-updated with a single component EKS. Databases will be outside only, they are not part of EKS Cluster as they are stateful.

In private subnet, we are replacing all the applications which are in it, with EKS Cluster.

In public subnet, we are placing application load balancer.

We will connect with eks cluster with the help of bastion or any client (workstation).

==> It is not safe to create resources which are not part of eks cluster like load balancer, listener, rule, target groups... It leads to unnecessary creation of service account, iam roles and givening permissions to them.

Rather than doing all this, we can create them through terraform.
--> We can create them before hand like lbs, bastion and simply attach our pods to the target group.

Above one app1, app2 are for practice purpose, now we create production grade cluster using terraform.


search target group binding in aws load balancer controller, this is safe to use when we are in cloud platform.

Using this, if we give target group arn, simply our pods go and attach to target group rather than creation and deletion in route53. But we require ingress controller drivers.
