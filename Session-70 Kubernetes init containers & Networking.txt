-----------------------

1. recreate
2. rolling update -> 2 versions running at same time (disadvantage)
3. blue/green -> Double cost (disadvantage), we can reduce replicas to 0
4. canary -> Send traffic to different version randomly, slowly ramping up from 0 to 100%
5. A/B testing -> Sending some traffic to other version based on location, headers, etc
6. shadow -> v2 is running but not accepting live traffic, we mock live traffic live traffic from v1 to v2, but we don't send response to end user

init containers:
================

Kubernetes secrets are encoded that anyone can easily decode it.

--> We must store secrets in secretsmanager
--> MySQL pod, MYSQL_ROOT_PASSWORD is required to setup

==> We can use init containers, these are the containers that run before main container runs. It prepares the env for main container like fetching secrets, checking the dependency services, running some sql scripts.

camping -> main
tent -> init container - prepares the environment

main container runs all the time.
init container runs to completion. You can have multiple init containers, they will be executed sequentially.


==> Steps involved to fetch secret using init container:

1. We should have IAM policy that can fetch the secrets
2. Create service account with this policy, IAM role will be created

3. Run the pod with this service account
4. Create init container that fetches secret and make it available in certain location -> containers in the pod can share storage. (Containers in the pod can have shared network and storage)
5. Main container reads it from the shared location, export it as env variable and remove that file

Network Policy:
==============

A NetworkPolicy in Kubernetes is used to control traffic flow between pods and/or external endpoints at the IP/port level. It acts like a firewall for pods.

By default, Kubernetes allows:

--> All pods to talk to each other
--> All ingress/egress traffic

NetworkPolicy lets you restrict that behavior for security.

Search network policy default deny in k8s

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: engineering
spec:
  podSelector: {}
  policyTypes:
    - Ingress

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: mongodb-catalogue
  namespace: roboshop
spec:
  podSelector:
    matchLabels:
      project: roboshop
      tier: database
      component: mongodb
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          project: roboshop
          tier: backend
          component: catalogue
    ports:
    - protocol: TCP
      port: 27017

Here, this policy is applied to mongodb and it is accepting from catalogue on port number 27017.

Pod Disruption Budget (PDB): search pdb k8s and take yaml file
============================

--> pod disruption means pod failure.

1 pod in some node

If node down -> app down

When we do this, node will be down:
--> node upgrade
 cordon
 drain
--> autoscaling (When cluster resources are less consumed) -> nodes will be deleted automatically, Then that pod comes out of that node and moves to another node.

In voluntary disruptions, pods may go down.

We can define PDB as, max how many number of pods can be unavailable.

2 pods -> 1 pod can go to unavailable

2 nodes

node-1 -> pod-1 -> success [If we drain node 1, it will become success because we told that 1 pod can go to unavailable]
node-2 -> pod-2

node-2 -> pod-1 and pod-2
before draining PDB comes into action
drain will be failed because PDB checks how many pods to become unavailable. Since, here 2 pods are available in node-2, it will fail.

Now, we add node-3
node-3 -> pod-2 should come here

single pod replica -> 25% of pods 
maxUnavailable -> 25%
minAvailable -> 25%

4 pods -> 1 pod should be always available means 25%

1 pod -> 25% max unavailable -> 0.25 pods should be always available -> 0 pods unavailable
2 pods -> 25% max unavailable -> 0.5 -> 0 pods unavailable
3 pods -> min available 25% -> 0.75 -> 0 pods can be available -> Can have downtime
4 -> 1 pod can go available
0.anything -> 0


10 pods -> 2 min available

4 nodes
========

node-1 -> If 4 pods are down -> still 6 pods are available -> success - drain

2 nodes
=======

node-1 -> If 9 pods are down -> can't drain because it will fail as min availability of pods are 2.


**********
In production, we should not go with one pod. Atleast, we should have 4 replicas (pods), when we can't handle downtime and when we think it becomes a problem then we use 4 replicas.

PDB
TopologySpreadConstraints -> spreading the pods across nodes based on topologyspreadconstraint otherwise Kubernetes assign 2 pods to one node only.

host as topology(border)
single AZ
2 nodes
If we specify host, it won't assign 2 pods to single node, it distributes the pods to both the nodes.
NODE-1 -> 1 pod is here
NODE-2 -> 1 pod is here

Two AZ
us-east-1a and us-east-1b

1 pod in us-east-1a AZ and another pod in us-east-1b AZ
topology is zone
host level topology

4 pods 
us-east-1a -> 2 nodes and us-east-1b -> 2 nodes

1st topology is zone -> k8s spreads pods across multi AZ
2nd topology is host -> 2 pods in same az spread across multi hosts

If we mix PDB and topologyspreadconstraint both properly, then keep our application running all the time and it won't become down any time. 
--> If in rare case node failure or total region goes down then our application also goes down we can't do anything for that as it is not in our control.
