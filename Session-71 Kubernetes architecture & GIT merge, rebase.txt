PDB:
----
A Pod Disruption Budget (PDB) defines how many pods of an application must stay running during voluntary disruptions.

--> Voluntary disruptions pod may go down.
Node maintenance (drain)
upgrade
delete pod


It ensures your application stays highly available even when Kubernetes or admins intentionally disrupt pods.

minAvailable → minimum number of pods that must be running
maxUnavailable → maximum number of pods that can go down

PDB does NOT stop:

--> Crashes
--> Node failures

==> It only controls intentional (voluntary) disruptions.


We can use minAvailable or maxUnavailable

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: zk-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: zookeeper

or 

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: zk-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: zookeeper

k8 architecture:
================

Cluster has control plane and nodegroup

control plane:
===============

1. api server -> Entry point for everything, checks authentication and authorization and call another components. We don't have access to other components.

2. scheduler -> Schedules the pod on available node, node resources, node selectors, affinity, anti affinity, taints and toleration, topologySpreadConstraint, PDB, etc.. It always checks pending pods can be scheduled or not

3. control manager
	replica/deployment controller -> Always checks desired number of replicas running or not
	Node controller:  Desired number of nodes are always up
	EndpointSlice controller: Always populates pod ips to service endpoints
	ServiceAccount controller: Create default ServiceAccounts for new namespaces
	
4. etcd -> Memory for k8s cluster, manifest files, config maps, secrets, etc., key-value pair database

5. cloud-controller-manager -> Cloud specific api handle

Node controller: For checking the cloud provider to determine if a node has been deleted in the cloud after it stops responding
Route controller: For setting up routes in the underlying cloud infrastructure
Service controller: For creating, updating and deleting cloud provider load balancers


node components:
================

kubelet -> Always in contact with api-server, it is like agent running in every node. node health status report sends to control plane, responsible to run the pods in node

kube-proxy -> Manages networking rules to bring traffic to pods, iptables management

Container runtime -> containerd, CRI-O is the run time

Branches:
=========

dev sit/uat/qa prod

DEV – Development
The environment where developers write and test code initially.

SIT – System Integration Testing
Testing where different modules or systems are combined and tested as a group.

UAT – User Acceptance Testing
Final testing done by end users or clients to verify the system meets business requirements.

QA – Quality Assurance
The process of ensuring the product meets quality standards through testing, reviews, and processes.

PROD – Production
This is the live environment where the application is actually used by real users. It’s the final stage after DEV → SIT → QA → UAT, and any changes here directly impact customers, so deployments are handled very carefully.

main -> prod ->
Create another branch, do the changes, test it and then push to main
PR -> When you bring change from another branch to main branch (pull requests)
