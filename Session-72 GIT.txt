Merge Vs Rebase: 
================

(Search merge vs rebase)
1. Merge creates extra commit, rebase will not create extra commit
2. Merge preserves history, rebase rewrites the history
3. Rebase changes the commit id references

--> If shared (multiple persons work on same branch) branch go with merge, if private/local (single person on individual branch) branch go for rebase. Rebase should be done in local branches only.
--> Merge is the safest option.

Branching strategy:
===================

Hotfix is used in Git workflows to mean a quick, urgent fix applied to production code.

--> A small, critical fix (e.g., bug, security issue)
--> Made directly against the production branch (main/master branch)
--> Release as soon as possible, without waiting for the next full release

How you bring changes in code from DEV -> PROD

develop -> uat -> production

==> If you software should support multiple versions at a time, then you can use branching strategy Ex: Instagram, VS Code.
--> If your software is purely web applications, then you no need to use this branching strategy as it is difficult to maintain.

git flow: (search git flow, a successful git branching model) It is used for desktop applications not for web/enterprise applications.
=========

merge and rebase -> merging strategy

master and develop
release

feature	-> source from develop, target release branch
release	-> source from develop, merge to master
develop	-> get changes from master

long lived branches
short lived branches

main, develop		-> long lived branches
short lived branches	-> release, feature, hotfix

main	-> Always points to production
develop	-> source=main, target=main


Feature branches:
=================

feature/1 -> source=develop, target=develop
feature/2 -> source=develop, target=develop

current	-> 2.53
release	-> 2.54	-> release/2.54 source=develop
Test the code into different environments like dev, uat (User Acceptance Testing), sit (System Integration Testing), etc.,
Create bug fixes branches and raise pull request (PR) to release branch
release/2.54 -> .exe .zip
Deploy to PROD
Then raise pull request (PR) to develop
main branch points to release/2.54 (tag)


2.53
2.53.1	-> hotfix/bugfix

Reset:
------
soft	-> It brings the changes from local repo to staging
mixed	-> It brings the changes from local repo to workspace
hard	-> Delete the changes

reset is used only for local branches. reset removes the commit id.

==> My code is in local repo, I have to undo it. Then, I can use git reset option to do that.

soft reset:	It brings the changes from local repo to staging
-----------
--> git reset --soft HEAD~1

git stash:
==========

You are working in some feature branch, suddenly you got emergency defect in production.

*******
==> When we are working in some feature branch, meanwhile you got sudden defect in master branch. We need to stash our changes and move to master, create hotfix and do the fix and come back to the feature branch using git stash pop and do the development.

git stash	-> Saves your code to stash memory
git stash pop	-> Brings your code to workspace

--> git checkout main
error: Your local changes to the following files would be overwritten by checkout:
        README.md
Please commit your changes or stash them before you switch branches.
Aborting

==>  git stash		[Saves your work anywhere in stash memory]

--> git checkout main	[Complete your work where you have conflicts and after that move to your working branch]

--> git checkout panner-dosa

--> git stash pop	[It brings back your code to workspace so that you can work on it]
