Declarative Vs Scripted pipeline:
=================================

Scripted pipeline	-> Old pipeline, groovy syntax. Before pipeline execution, it can't check for errors. At run time, if error comes it will exit. We have more control to write scripts. Starts with node.
Declarative pipeline	-> Latest pipeline from jenkins 2.0. It allows groovy syntax, but before execution it check for errors. We have to do whatever the code they give after installing plugins in this declarative pipeline.

We use a hybrid approach, we have script block in our declarative pipeline to have more control on the stages. (Mixing both the pipelines and use to get the better results).

--> The script step takes a block of Scripted Pipeline and executes that in the Declarative Pipeline.

Master and Node/Master Agent architecture:
==========================================

--> We have only one Jenkins for each project. But, we have lot of components like catalogue, cart, user... To get nodejs, java and so on capabilities for Jenkins, we add them and Jenkins will get lot of load on it. To overcome this, we use master and node architecture, so that Jenkins don't get load on it and distributes the work loads to agents same as EKS Master Node (It doesn't run any work loads).

If we trigger pipeline in jenkins, then according to our project jenkins allocates the work to different agents as per the requirement. Basically through jenkins we can connect to any server. In companies, jenkins agents will have full permissions. So, we have do any work through jenkins only because we can have clear visualization, logs... If we give ssh access then they will not know what we are doing, so they will restrict us using through ssh. Whatever we want to do, do it through jenkins.

--> If jenkins is having access to all the servers, we can write anything not only pipeline, you can write some scripts to execute and so on.

POST:
=====

The post section defines one or more additional steps that are run upon the completion of a Pipeline’s or stage’s run (depending on the location of the post section within the Pipeline). 

pre-build
build
post-build

Based on the status, we can take the actions.

post build:
-----------
post { 
        always { 
            echo 'I will always say Hello again!'
        }
        success { 
            echo 'Pipeline success'
        }
        failure { 
            echo 'Pipeline failure'
        }
    }

==> If we don't specify success and failure, then it will always show the output as always.
==> If we have specified them, then it will show the desired output based on the given build along with the always. If exit 1 is given in build section as it is a failure, it will display failure output and always output. Otherwise, we will be getting success along with always output.

PARAMETERS:
===========

It provides a list of parameters that a user should provide when triggering the Pipeline. The values for these user-specified parameters are made available to Pipeline steps via the params object, refer to the Parameters, Declarative Pipeline for its specific usage.

Each parameter has a Name and Value, depending on the parameter type.

parameters {
        string(name: 'PERSON', defaultValue: 'Mr Jenkins', description: 'Who should I say hello to?')

        choice(name: 'CHOICE', choices: ['One', 'Two', 'Three'], description: 'Pick something')
        password(name: 'PASSWORD', defaultValue: 'SECRET', description: 'Enter a password')
}


steps {
	script {

   			echo "Testing"

  	 		echo "Toggle: ${params.TOGGLE}"
   			echo "Choice: ${params.CHOICE}"
   			echo "Password: ${params.PASSWORD}"
		""""
	}
}

Build periodically (Monolithic applications) has:
This field follows the syntax of cron (with minor differences). Specifically, each line consists of 5 fields separated by TAB or whitespace:
MINUTE HOUR DOM MONTH DOW
MINUTE	Minutes within the hour (0–59)
HOUR	The hour of the day (0–23)
DOM	The day of the month (1–31)
MONTH	The month (1–12)
DOW	The day of the week (0–7) where 0 and 7 are Sunday.
To specify multiple values for one field, the following operators are available. In the order of precedence,

* specifies all valid values
M-N specifies a range of values
M-N/X or */X steps by intervals of X through the specified range or whole valid range
A,B,...,Z enumerates multiple values
To allow periodically scheduled tasks to produce even load on the system, the symbol H (for “hash”) should be used wherever possible. For example, using 0 0 * * * for a dozen daily jobs will cause a large spike at midnight. In contrast, using H H * * * would still execute each job once a day, but not all at the same time, better using limited resources.

The H symbol can be used with a range. For example, H H(0-7) * * * means some time between 12:00 AM (midnight) to 7:59 AM. You can also use step intervals with H, with or without ranges.

Ex:
```
# Every fifteen minutes (perhaps at :07, :22, :37, :52):
H/15 * * * *
# Every ten minutes in the first half of every hour (three times, perhaps at :04, :14, :24):
H(0-29)/10 * * * *
# Once every two hours at 45 minutes past the hour starting at 9:45 AM and finishing at 3:45 PM every weekday:
45 9-16/2 * * 1-5
# Once in every two hour slot between 8 AM and 4 PM every weekday (perhaps at 9:38 AM, 11:38 AM, 1:38 PM, 3:38 PM):
H H(8-15)/2 * * 1-5
# Once a day on the 1st and 15th of every month except December:
H H 1,15 1-11 *
