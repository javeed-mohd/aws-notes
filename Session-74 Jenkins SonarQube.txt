Input:
======
--> In Jenkins folder for manual approval, we write input { } condition in our code. This allows you to prompt for input, using the input step. The stage will pause after any options have been applied, and before entering the agent block for that stage or evaluating the when condition of the stage. If the input is approved, the stage will then continue.

	stage('Example') {
            input {
                message "Should we continue?"
                ok "Yes, we should."
                submitter "alice,bob"
                parameters {
                    string(name: 'PERSON', defaultValue: 'Mr Jenkins', description: 'Who should I say hello to?')
                }
            }
            steps {
                echo "Hello, ${PERSON}, nice to meet you."
            }
        }

--> This is how, we can put some gates to approve or not for building and deploying the images.


When:
=====

The when directive allows the Pipeline to determine whether the stage should be executed depending on the given condition. The when directive must contain at least one condition. If the when directive contains more than one condition, all the child conditions must return true for the stage to execute. This is the same as if the child conditions were nested in an allOf condition. If an anyOf condition is used, note that the condition skips remaining tests as soon as the first "true" condition is found.

Based on the branches and custom parameters, we can use this condition to allow or not.

	stage('Deploy') {
            when {
                expression { "${params.DEPLOY}" == "true" }
            }
	}

The SonarScanner CLI is a code analysis scanner for CI/CD pipelines, used when no build-system-specific scanner is available. Distinct from the SonarQube CLI, a developer management interface.

--> sonar.exclusions excludes the files mentioned there and scans only source code which are not excluded. We only need to scan the application code. So, we will have sonar.exclusions line. (search sonar exclusions property)

==> The sonar.exclusions property is used to define path-matching patterns for files or directories that should be completely filtered out from a SonarQube or SonarCloud analysis.

sonar.exclusionsExcludes		--> Specific source files from all analysis.
sonar.test.exclusionsExcludes		--> Specific test files from analysis.
sonar.coverage.exclusionsExcludes	--> Files from code coverage reports while still analyzing them for code quality issues.
sonar.cpd.exclusionsExcludes		--> Files from duplication detection (Copy-Paste Detection).


Pattern Syntax Exclusions use a comma-separated list of wildcard patterns:
*: Matches zero or more characters.
**: Matches zero or more directories.
?: Matches a single character.

Common Examples:
**/node_modules/**: Excludes everything in any node_modules directory.
**/*.java: Excludes all Java files in the project.
src/generated/**/*: Excludes all files within the src/generated folder.

Vulnerabilities		--> Issues in code that can be used by attackers to exploit

Bugs			--> Bugs that can cause unexpected behaviour in runtime

Security Hotspots	--> SAST (Static Application Security Testing) scans code and finds both vulnerabilities and hotspots

==> Vulnerabilities
Weaknesses in code that can be exploited by attackers, leading to security risks (e.g., SQL injection)

Bugs
Issues in code that cause incorrect or unexpected behavior during execution

Code Smells
Poor coding practices that don’t break functionality but make code hard to maintain, read, or extend

Coverage
The percentage of code executed by automated tests (usually unit tests)

Duplications
Repeated blocks of code that should be refactored to improve maintainability

Security Hotspots
Code sections that are potentially sensitive and need manual review, not necessarily vulnerabilities
(e.g., authentication logic, encryption usage)
