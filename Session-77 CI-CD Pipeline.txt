What are the stages you have in your pipeline/ promoting the application from dev to PROD deployment?
We are following feature branching strategy, main and feature branch. Whenever there is a change, developers create a feature branch and then immediately our pipeline will be triggered. We are following shift-left strategy, we are doing sonar scan, trivy scan (image scanning), library scan (GitHub dependabot). We are running unit test cases, building the image and pushing the image to ECR repo (roboshop/catalogue), then feature branch is completed. Then, developers will go and raise a pull request (PR) to main branch. Before merging feature to main, we applied a setting like minimum approvals required are 2 and it should pass all the status checks provided (scans and tests).
Once, this two conditions are met, then we are allowing them to merge. After successful merging the code to main branch, then we are immediately triggering our main pipeline that will by default deploy to development environment and our testing team configures the test cases of what they have written API/Functional, we are triggering the test cases as well. If the deployment and testing both are successful, our pipeline is creating a JIRA ticket and there we will get an option for Trigger UAT Deploy. So, developers will go and check is everything is fine in development environment, then they will trigger UAT for the JIRA. Then our pipeline will deploy the application into UAT. So, then again our testing team will configure end to end/integration testing. If deployment and end to end testing is successful in UAT environment, then we have to start change management process/change request (CR). Support team will raise a CR request with all the details like date and time, change, version, project, component and everything. They have to give that CR Number to JIRA. So, now developers/Devops support team (L2) can trigger the PROD pipeline from JIRA. [But, in pipeline we are checking that they must provide the CR number. Without CR Number, we do not trigger the PROD deployment}. When they give use CR Number, we are checking whether the CR is completely approved and the trigger is within the time frame or not. If CR is approved and time is within the deployment window, then we are performing to the PROD Deployment and then once the PROD Deployment is successful, we are tagging the main branch commit-id with the version.

==> We have two types of Pipeline, one is feature branch and other is main branch pipeline. We are following multi-branch pipeline. When developer is committed some change into feature branch, the stages are like obviously code will be cloned, we are reading the version from package.json and we are running unit test cases, sonar scan, we have implemented quality gates in sonar scan where issues, vulnerabilities, bugs should be zero and code coverage should meet at least 80%, maintainability and security ratings should be 'A' and we will wait for quality gate to clear, if it is successful, do the library scan (GitHub dependabot), we will build the docker image and scan the image using trivy scan (image scanning). If everything is successful, we are pushing the image to ECR repo. This is our feature branch pipeline. Then, developers will go and raise a pull request (PR). Once the code comes to main branch, we will trigger main pipeline that will deploy the application into development environment, trigger the API/Functional test cases written by our testing team and if it is successful, we are creating the JIRA Ticket there developers will get an option to trigger UAT Deploy, then they will trigger it Again our main pipeline will be called, now we will deploy the application to UAT Cluster where end to end/integration testing will be done. If everything goes well, we will consider UAT Passed. Then, next stage is PROD. All the CR process will happen and then deployment window opens our development/support team will trigger the deployment to PROD that will call our pipeline again, deploy to PROD, if it is successful, tag the git commit-id with the version. And we cannot tag the same version in git.
